# Contact delivery security review

Scope: source-level inspection of the app and new `POST /api/contact` path, with automated negative tests. This is not a live provider, DNS or Cloudflare assessment.

No Git repository metadata is present in this workspace, so committed history could not be audited. The check covers the working source, empty environment template, ignored environment patterns and generated client JavaScript bundles.

- **Secrets:** environment reads occur only in a `server-only` module. Email/store modules and the handler also import the guard. No `NEXT_PUBLIC_*` secrets, real credentials, or hardcoded provider tokens were added. `.env*` is ignored except the empty `.env.example`. Tests use clearly labeled fixtures injected into mocks, never live credentials.
- **Endpoint authority:** there is exactly one delivery route, POST only. Recipient, From, subject template, plain-text body format and provider URLs are server-controlled. Client `to`, `from`, `subject`, `html`, attachments, arbitrary services, unknown package IDs and all other unexpected properties are rejected. No account, database for enquiries, admin, payment or authentication system was created.
- **Validation:** schema validation runs on the server regardless of browser behavior. It checks required keys, primitive types, lengths, format, control characters, honeypot and package allowlist. Byte-counted streamed reads reject oversized/malformed JSON/UTF-8, and a timeout bounds reads. Compression and media types other than JSON are rejected. Browser Origin is checked against a server-configured exact allowlist; no CORS permission is granted. Origin is not treated as proof that a requester is human.
- **Abuse protection:** every delivery path passes shared atomic Redis budgets; failures block sending. No in-memory production limiter or untrusted IP-header identity is used. Global budgets cap forged-email abuse; per-email budgets slow repeats. Honeypot failures use the same generic 400 response as other malformed submissions. 429 responses contain a controlled message and retry interval.
- **Duplicates:** Redis claim states are shared across instances. Identical accepted submissions do not resend. Pending submissions cannot claim another delivery lease. Provider retries reuse a server-generated idempotency key and stable timestamp/body. Client in-flight refs and disabled buttons prevent UI double submission, but they are not the security boundary. Data edits generate a new request ID.
- **Submitted content:** emails use plain text only. Visitor content is not passed to HTML rendering, templates, shell commands or URL fetches. Name/email header control characters are rejected. The visitor is Reply-To only. No raw content appears in server logs.
- **Errors:** configuration, rate-store and provider failures return a generic Norwegian response. Logs contain fixed event categories only, no exceptions, tokens, addresses or payloads. Success requires a provider acceptance ID or a stored previous acceptance. Responses are non-cacheable.
- **Limits:** bot traffic can exhaust the intentionally conservative global budget; edge protection and monitoring are needed. Deduplication lasts 24 hours and does not survive a new browser-generated ID after reload. Provider acceptance is not guaranteed inbox delivery. Browser Origin checks do not prevent direct scripted submissions. Lua/REST integration and provider acceptance are exercised through mocked adapters locally; verify the provisioned Redis scripts and Resend delivery before launch. No real email was sent during local tests.
- **Future authorization:** if accounts, admin, payments or private records are introduced, enforce authorization server-side on every protected endpoint. Hidden UI or client routing is never an access-control boundary.
